1. Resumen ejecutivo

El dominio raíz web.opynio.com sólo aceptaba paths en español. Cualquier intento de acceder a una traducción (/login, /register, /preise, /prezzi, /pricing…) era redirigido a /404 con un HTTP real, aunque las rutas estuvieran registradas para todos los idiomas. Adicionalmente, varios componentes generaban links internos hardcoded a la versión española (pathTranslations.es.X), produciendo navegación inconsistente para usuarios en otros idiomas, y todo el subárbol del business dashboard sólo estaba registrado en español.

Se aplicaron 5 commits que: (a) abren el dominio raíz a las 8 traducciones, (b) sincronizan automáticamente el idioma de la UI con el path al que entra el usuario, (c) registran rutas multilingües para el dashboard del business, (d) corrigen los links internos para respetar idioma/país, y (e) actualizan robots.txt para cubrir las nuevas variantes. Pendiente queda una mitigación SEO (canonical inteligente) para evitar contenido duplicado en el dominio raíz.

2. El bug — qué pasaba

Síntoma observado por el usuario Tipear web.opynio.com/register en el navegador devolvía la página interna /404 ("Pagina no encontrada"). Lo mismo con /login (en), /preise (de), /prezzi (it), /connexion (fr), /cadastro (br), etc. La única versión que funcionaba era el path en español equivalente (/registro, /acceder, /planes…).

Adicionalmente, dentro del business dashboard, las URLs no españolas también caían al 404:

URL probadaResultado anterior
/us/business/dashboard/X/reviews404
/fr/entreprise/tableau-de-bord/X/avis404
/de/unternehmen/dashboard/X/bewertungen404
/it/azienda/cruscotto/X/recensioni404
/es/empresa/panel/X/resenasOK ✓

Y al hacer login estando en /us, el redirect post-login mandaba al usuario a /post-acceso (path español, sin country prefix) en vez de a /us/post-login.

3. Causa raíz — por qué arrojaba 404

El bug no tenía una sola causa, sino tres capas independientes que se alineaban para producir el mismo síntoma:

3.1. Validador de paths con regla "solo español en raíz"

En App.tsx, el componente LanguagePathValidator tenía esta lógica (Case 1) cuando la URL no incluía country prefix:

if (!countryCode) {
    // ...
    const isValidForSpanish = Object.values(spanishPaths).some(...);
    if (isValidForSpanish) return <>{children}</>;

    // Si el path es válido en otro idioma, forzar 404
    const pathKey = getPathKeyFromPath(currentPathSegment);
    if (pathKey) {
        setShouldShow404(true);  // ← redirige a /404 con HTTP real
    }
}

Lógica explícita: "el dominio raíz solo acepta paths en español; si el path es válido pero en otro idioma, devuelve 404". Esta regla existía por una preocupación SEO previa (evitar duplicate content), pero rompía el caso de uso del usuario directo.

3.2. Subárbol del business dashboard hardcoded a español

Las rutas del dashboard del business estaban registradas con pathTranslations.es.X directamente:

<Route path={pathTranslations.es.businessDashboard} element={...}>
    <Route index element={<DashboardOverview />} />
    <Route path={pathTranslations.es.dashboardReviews} element={...} />
    <Route path={pathTranslations.es.dashboardAnalytics} element={...} />
    {/* ... */}
</Route>

Resultado: solo /es/empresa/panel/:name/resenas matcheaba. Las traducciones a otros idiomas (business/dashboard/:name/reviews, entreprise/tableau-de-bord/:name/avis, etc.) no tenían ningún <Route> registrado, así que caían al catch-all * → NotFoundPage.

3.3. Links internos hardcoded

Varios componentes construían URLs así:

// LoginPage.tsx
navigate(`/${pathTranslations.es.postLogin}`);

// PricingPage.tsx
ctaLinkTarget = `/${pathTranslations.es.assignBusiness}?plan=...`;

// ProfilePage.tsx
<Link to={`/${pathTranslations.es.editProfile}`}>...

// BusinessListPage.tsx (botón "Gestionar")
const dashboardPath = pathTranslations.es.businessDashboard.replace(...);

// BusinessDashboardPage.tsx (redirect UUID→nombre)
const newPath = `/${pathTranslations.es.businessDashboard.replace(...)}`;

Aunque el usuario navegara en /us/..., todos estos clicks reconducían a paths en español sin country prefix. El validator (3.1) los aceptaba (porque son paths españoles válidos), pero la UX quedaba inconsistente: navegabas en inglés y de pronto la URL cambiaba a /perfil/editar.

4. Por qué lo arreglamos

Decisión de producto Opynio ofrece la web en 8 idiomas (es / en / fr / de / it / br / ca / cn). Si las rutas están registradas para todos los idiomas, los usuarios deberían poder llegar a ellas escribiendo la URL directa, sin tener que adivinar el country prefix correcto. Bloquear estas URLs convertía un sitio multilingüe en uno "español + alias por país", lo cual no era el modelo mental ni del producto ni del usuario.

Razones concretas para justificar el cambio:

  • UX directo: un usuario alemán que recibe el link /preise en un email espera ver Preise, no un 404.
  • Coherencia interna: el helper uniquePaths en App.tsx ya iteraba los 8 idiomas para registrar rutas raíz; el validator estaba contradiciendo esa intención registrada.
  • Casos cross-border: usuarios bilingües, links compartidos entre países, etc. — el dominio raíz (sin país) es la URL más común para compartir externamente.
  • SEO multilingüe correcto: el sitio ya genera hreflang para todos los idiomas vía Meta.tsx; tener URLs accesibles que respondan 404 era una contradicción interna.

El subárbol del dashboard se arregla por la misma lógica: si la app reconoce un dueño con empresa en US y lo lleva a /us/business/dashboard/X, no puede caer en 404 a media navegación porque el panel solo esté registrado en español.

6. Cambios aplicados (cronológicos)

6.1 f113cac — Dashboard multilingüe

En App.tsx, el subárbol businessDashboard + sus 6 children se registra ahora con uniquePaths (que itera los 8 idiomas) en lugar de pathTranslations.es.X. Aplicado tanto al bloque raíz como al bloque country-prefixed. Las URLs /us/business/dashboard/X/reviews, /fr/entreprise/tableau-de-bord/X/avis, etc., dejan de tirar 404.

6.2 c5a3d75 — Validator acepta cualquier idioma en raíz

Se elimina la regla "solo español" del Case 1 de LanguagePathValidator. El dominio raíz acepta paths en cualquier idioma; los rutas registradas en uniquePaths los manejan, y los inválidos caen al catch-all *. Adicionalmente, en MainLayout se añade un nuevo useEffect que detecta el idioma del primer segmento del path (helper detectLanguageFromPath) y sincroniza el contexto i18n para que el Header/Footer se rendericen en el idioma correcto.

Case 2 (rutas con country prefix) se mantiene intacto: /us/registro sigue dando 404 correctamente porque el país manda en su prefijo.

6.3 db71a2e — Links internos respetan idioma/país

Sustituye pathTranslations.es.X por pathTranslations[language].X en:

  • LoginPage.tsx — postLogin tras sign-in
  • PricingPage.tsx — CTA assignBusiness
  • ProfilePage.tsx — links a editProfile y writeReview
  • BusinessListPage.tsx — botón "Gestionar" usa idioma del país del business + country prefix
  • BusinessDashboardPage.tsx — redirect UUID→nombre conserva country prefix actual e idioma del business
  • EditBusinessPage.tsx — botón "Cancelar" respeta país/idioma del business

6.4 10faa79 — Legacy redirect soporta UUID

LegacyBusinessRedirect ahora detecta UUID con regex y usa getBusinessById en ese caso (antes siempre llamaba a getBusinessByName(UUID) → null → 404). Las notificaciones push, que incrustan related_business_id y abren /empresa/<UUID>, ya resuelven a la página correcta del business.

6.5 9297835 — robots.txt multilingüe

Se amplía el archivo para cubrir los 21 country prefixes válidos y todas las traducciones de paths privados (perfil, post-login, dashboard, write-review, assign-business, my-businesses, payment-success/cancel, forgot/reset password, migrate-google-reviews) y públicos (empresa/business/entreprise/unternehmen/azienda; faq/about/how-it-works en sus traducciones).

7. Impacto en SEO y mitigación canonical

Riesgo identificado: contenido duplicado en el dominio raíz El cambio c5a3d75 abre el dominio raíz a paths multilingües. Como el sitio también responde con country prefix, ahora coexisten URLs equivalentes:
  • /login y /us/login y /gb/login — mismo Login en inglés
  • /preise y /de/preise — misma página en alemán
  • /prezzi y /it/prezzi — misma página en italiano
Sin canonical explícito, Google puede ver duplicados y diluir link equity.

7.1 Cambios que NO afectan SEO (o lo mejoran)

  • Dashboard multilingüe — todas las rutas están Disallow en robots.txt; SEO neutro.
  • Links internos correctos — mejora SEO (menos 404s, mejores señales de navegación interna).
  • Legacy UUID fix — mejora SEO (menos 404s en clicks de notificaciones).
  • robots.txt ampliado — mejora SEO (mejor guía de crawl, anti-duplicate rules más completas).
  • URL pública de share por país — mejora SEO (links externos llegan al idioma correcto del business).

7.2 Mitigación: canonical inteligente (Opción 1)

Para neutralizar el duplicate content sin retroceder en UX, se aplicará lógica en Meta.tsx: cuando un path en raíz pertenezca a un idioma no-español, su canonical apuntará al equivalente con country prefix por defecto.

URL accedidaCanonical declaradoResultado en Google
/login/us/loginPágina alternativa, no se indexa
/preise/de/preisePágina alternativa, no se indexa
/prezzi/it/prezziPágina alternativa, no se indexa
/registro (es)/registro (raíz)Indexa raíz como versión española
/us/login/us/loginIndexa como versión inglesa US

Mapeo idioma → país por defecto que se usará para construir el canonical:

  • en → us  |  de → de  |  fr → fr  |  it → it
  • br → br  |  ca → ad  |  cn → cn
  • es → ninguno (el dominio raíz es la versión canónica española)

Para usuarios este cambio es invisible. Para Google: cero duplicate content, link equity consolidado a una URL por idioma, Search Console limpio.

8. Verificación y rollback

8.1 Cómo validar manualmente

  • Probar en producción cada URL del cuadro de auditoría (sección 5) y confirmar que renderiza la página esperada con la UI en el idioma correcto.
  • En Search Console: revisar el reporte "Cobertura" tras 1-2 semanas para confirmar que las URLs raíz multilingües aparecen como "Página alternativa con etiqueta canónica adecuada" (no como duplicados).
  • Probar el flujo "click en notificación push" → debe abrir el perfil de empresa correcto sin pasar por 404.
  • Probar OAuth + login con cuenta en /us → debe redirigir a /us/post-login, no a /post-acceso.

8.2 Cómo revertir si fuera necesario

Cada cambio es un commit independiente y atómico:
